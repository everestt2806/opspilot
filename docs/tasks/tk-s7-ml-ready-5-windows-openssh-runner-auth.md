### UPDATE 21/10 — BOM root cause and repair

- Offline inspection used the existing Electron safeStorage flow on `%TEMP%\\opspilot-live0-20261020`; SQLite was query-only. The credential's UTF-8 plaintext round-tripped through stdin. Metadata showed OpenSSH private-key container, leading UTF-8 BOM, LF line endings, terminal newline and no literal `\\n`. Old materialization retained the BOM and Windows OpenSSH rejected the file. The new protected temp file matched the handed bytes after removing only the BOM; `ssh-keygen -y -P '' -f <protected-temp-key>` parsed successfully. No credential or key hash was recorded.
- Root cause: the stored credential text had a UTF-8 BOM before the OpenSSH PEM marker, which Windows OpenSSH interpreted as key data. The previous fixture covered CRLF produced from LF but not BOM-prefixed input. The fix strips only the leading U+FEFF and writes UTF-8 bytes directly, preserving source LF/CRLF exactly and preventing platform newline conversion.
- Regression generates disposable Ed25519 fixtures with BOM+LF and BOM+CRLF. Both fail direct OpenSSH parsing with BOM; after materialization, both parse and produce exactly the original public-key output. Temp cleanup and restricted ACL path pass.
- One post-fix live launcher run used the same profile clone, saved pin and endpoint. The experiment runner itself passed `SSH_HOST_KEY`, `SSH_TRANSPORT`, its fixed read-only clock command and resource inventory. No SshManager/snapshot evidence was substituted.
